Turns a project just created by `laravel new` into the house baseline: the guardrails that make agents write good Laravel. Run from the project root. The files to install live in this skill's `assets/` folder; copy them verbatim. They were verified against Laravel 13 · Filament 5 · PHP 8.5.

The run is finished when `composer test` is green on top of a history of small, single-concern commits. Every command below runs with `--no-interaction` where it accepts it; when a command still prompts, hand it to the user to run in their terminal and wait.

## 1. Survey and decide

Read `composer.json`, `php artisan --version`, `php -v`, `git status`, `git log --oneline`. Note whether a starter kit was installed (`livewire/flux` or `livewire/livewire` in `require`) and whether Pest is in `require-dev`.

Ask the user both questions in one message and wait:

1. **Backoffice?** Does the app need a Filament admin panel? A backoffice app is admin-only: the Filament login _is_ the app's login, and `laravel new` should have had **No** starter kit. If they want a backoffice and a starter kit is installed, say so and let them choose: a Filament panel on top of the starter kit (two logins), or recreate the project without a starter kit.
2. **API?** Does the app expose an API that needs authentication?

Stop and ask before continuing if Laravel is not 13.x or PHP is below 8.2: the assets assume that stack.

Commit the untouched skeleton (`git init` first if needed) as `chore: fresh laravel skeleton`, so every later change diffs against it.

Done when both answers are confirmed and the skeleton is committed.

## 2. Backoffice — only if the user said yes

```bash
composer require filament/filament:"^5.0"
php artisan filament:install --panels --no-interaction
```

Filament brings Livewire with it. Done when `app/Providers/Filament/AdminPanelProvider.php` exists and is listed in `bootstrap/providers.php` (add it if missing). Commit: `chore: install filament panel`.

## 3. Tooling and rules

1. Dev dependencies; add `pestphp/pest --with-all-dependencies` too if Pest is missing:

   ```bash
   composer require --dev larastan/larastan rector/rector driftingly/rector-laravel
   ```

2. Copy the assets:

   | Asset | Destination |
   | --- | --- |
   | `pint.json`, `phpstan.neon`, `rector.php` | project root |
   | `Pest.php` | `tests/Pest.php` (replaces the generated one) |
   | `rules/*.md` (including `index.md`) | `.ai/rules/` |

   The house conventions ship as Boost **project rules**: path-scoped Markdown in `.ai/rules/`, each file's `paths` frontmatter naming the globs it governs, and `index.md` mapping globs to files. Boost's core guideline sends agents to `index.md` before they plan or edit. Rules are read live, so a rule edited later takes effect without reinstalling Boost.

3. Merge the `scripts` object from `assets/composer-scripts.json` into `composer.json`: add its keys, replace the generated `test` script, keep every other existing key (`post-autoload-dump`, `dev`, `setup`, …). Check with `composer validate --no-check-publish`.

4. Install Boost:

   ```bash
   composer require laravel/boost --dev
   php artisan boost:install --no-interaction --guidelines --skills --mcp
   ```

   If `php artisan list boost` shows `boost:index-rules`, run it: it regenerates `index.md` from the rule files and warns about any file without valid `paths`.

   Done when the guideline file Boost wrote (named in its output, e.g. `CLAUDE.md` or `AGENTS.md`) has the **Project Rules** section pointing at `.ai/rules/index.md`, and `index.md` lists every rule file. If the guideline file is missing, ask the user to run `php artisan boost:install` in their terminal, choosing their agents, then check again.

Commit: `chore: add house tooling, rules and boost`.

## 4. API — only if the user said yes

```bash
php artisan install:api --no-interaction
composer require dedoc/scramble
```

Add the `Laravel\Sanctum\HasApiTokens` trait to `App\Models\User`. Scramble serves docs at `/docs/api` in the `local` environment only; keep that default — exposing them elsewhere goes through a `viewApiDocs` gate, the user's call. Commit: `chore: add sanctum and scramble`.

## 5. Normalize

This runs last so it covers code generated by every install above. Pint enforces strict types, `final` classes, immutable dates and strict comparisons; Rector adds types and dead-code removal; PHPStan runs at level 8. The generated skeleton was written to none of these.

1. Run `composer lint` and commit it alone: `chore: normalize skeleton to house standards`. Before committing, read the diff for Rector changes that alter behaviour rather than form (type declarations on framework code especially) and keep a list for the report.
2. Run `composer test` and fix until it exits 0:
   - Lint check still failing → rerun `composer lint` until Pint and Rector agree.
   - PHPStan errors in generated code → fix the ones with a local, obvious fix; baseline the rest with `vendor/bin/phpstan analyse --generate-baseline` and add `phpstan-baseline.neon` to `includes` in `phpstan.neon`.
   - Test failures → the house `Pest.php` applies `RefreshDatabase` to Feature and Unit tests, freezes time, fakes `Sleep` and blocks stray HTTP; adapt the test to that.

   Keep the standards fixed: PHPStan level 8, every Pint rule, every Rector set. If a rule looks genuinely wrong for this project, stop and ask the user.
3. Commit the fixes: `chore: make generated code pass house checks`.

Done when `composer test` exits 0.

## 6. Report

- Choices: backoffice yes/no, API yes/no.
- Commits made, hash and subject.
- `composer test` result — the real output if it is red.
- Behaviour-changing Rector edits, and how many PHPStan errors went to the baseline.
- What the user does next: `php artisan make:filament-user` (backoffice); `$middleware->statefulApi()` plus CORS/cookie config if a first-party SPA will consume the API.
- Every point where reality diverged from this skill (a command that prompted, a flag that changed, a fix the skeleton needed), so the skill can be updated.
